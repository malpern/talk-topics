02 · Why this foundation matters

This is bigger than one Vim command.

A native Mac tool can only automate web text safely if Chrome’s value, selection, and replacement APIs describe the same characters. The current mismatch weakens every higher-level capability built on that foundation.

KINDAVIM

Text motions need exact boundaries.

Commands such as move, delete, change, or operate across lines start with a selection range. If that first range drifts, the higher-level command cannot be trustworthy.

BEAR AUTOMATION

Text handoffs must preserve meaning.

Workflows that select, copy, transform, or replace Chrome text before sending it to Bear need the selected content—not merely the returned numbers—to match the intended slice.

AI ON THE MAC

Accessibility is the universal fallback.

When an app exposes no dedicated automation API, an agent reads and edits ordinary fields through macOS Accessibility. A reliable text contract makes that general path possible.

The broader capability ladder

Each step depends on the steps below it. We will investigate and file these as narrow contracts, not present one giant “fix all automation” change.

1 · Exact textThe exposed value is a stable character snapshot.
2 · Select + replaceRanges select the same characters and edits land at the intended boundaries. Current first bug.
3 · Lines + markersLine ranges, text markers, and paragraph boundaries agree.
4 · Geometry + styleBounds and attributed text refer to the same range space.
5 · Rich automationKindaVim motions, Bear workflows, and AI editing compose safely.

Why start here: selected range + selected text is small enough to prove with one fixture and focused regression tests, yet foundational enough to unlock and de-risk every later capability.

04 · The proposed solution

Map meaning, not just numbers.

Keep the DOM unchanged. Introduce a reversible mapper between the exact exposed-value snapshot and representable accessibility-tree boundaries.

✓

The invariantAn API range defined relative to one accessible value uses offsets from that same immutable character snapshot.

↔

Reversible

Generated separators map to boundaries without becoming literal DOM characters.

⏱

Snapshot-safe

Do not mix offsets from one tree/value state with another.

⊘

Fail closed

Do not silently select different text when mapping is stale or invalid.

⌁

Compact

Store only the separator metadata the immediate consumer needs.

The owner decision

Where should the mapper live?

Our evidence establishes the required behavior, not the final architecture. Chromium’s accessibility owner should choose the smallest maintainable placement.

A

Cocoa-local mapping

Narrow platform surface and lower initial scope. May repeat work if other APIs need the same coordinates.

or
B

Shared compact metadata

Reusable and consistent across consumers. Carries cache invalidation, memory, and cross-tree review costs.

05 · Think like a Chromium owner

Prove one contract.
Keep the first change small.

The owner’s job is not to approve a KindaVim workaround. It is to protect Chrome’s platform contract, performance, maintainability, and regression surface.

Six questions the owner will ask

01Is the platform behavior independently wrong?Chrome and Canary disagree with their own AXValue; Safari supplies a native differential.
02Is there a minimal live reproducer?Three block children and four exact native range queries.
03Does the regression fail before the fix?The test must establish that on current main before implementation is ported.
04What invalidates the mapping?Dynamic edits, subtree changes, cross-tree boundaries, and snapshot mismatch need explicit behavior.
05What does it cost?Keep metadata compact and measure large editable trees if shared caching is proposed.
06Can the change be reviewed alone?One behavior, one platform, one bug, one coherent regression.

Chrome exposes generated paragraph separators in a macOS editable object’s AXValue, but selection APIs interpret later offsets in separator-free DOM text.
