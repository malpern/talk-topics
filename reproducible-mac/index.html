Chapter one

New laptop, now what?

You unbox a new Mac and feel it: two days of "wait… how did I set that up?" Reinstalling tools from memory, hunting down old config, re-pasting API keys from wherever they ended up. The install isn't the hard part — reconstruction from memory is.

And there's a quieter, nastier version of the same problem: drift. Two machines that started identical and slowly diverged, each accumulating little undocumented tweaks.

My Mac mini — a headless CI runner — had silently let its GitHub Actions runner deregister, and its .gitconfig had ballooned to 2,581 lines (CI appended a safe.directory entry on every single job). "Works on my machine," at the level of the machine itself.

The fix isn't discipline. It's making the machine something you can rebuild — a repo, not a snowflake.

Chapter two

The principle

Three rules carry the whole thing:

  • Declarative state in git — what should exist: your dotfiles, a Brewfile, your app configs. This is the source of truth.
  • A thin, idempotent bootstrap.sh — it applies that state, and is safe to run a hundred times. Run it on a fresh Mac and it installs everything; run it on a configured one and it changes nothing.
  • Secrets out-of-band — never plaintext in the repo (Chapter 4).

Plus one modifier that does a lot of work: host-aware. One repo, many machines — each gets the slice it needs.

Chapter three

The build

The bootstrap installs its own prerequisites, so it works from a genuinely blank Mac:

# Command Line Tools → Homebrew → oh-my-zsh, only if missing
xcode-select -p &>/dev/null || xcode-select --install
command -v brew &>/dev/null || /bin/bash -c "$(curl -fsSL …/install.sh)"
[ -d ~/.oh-my-zsh ]         || RUNZSH=no KEEP_ZSHRC=yes \
                                sh -c "$(curl -fsSL …/ohmyzsh/install.sh)"

# then: symlink dotfiles, trust taps, brew bundle, uv tool install …

Every step is guarded — that's what makes it idempotent. KEEP_ZSHRC=yes matters: without it, the oh-my-zsh installer would clobber the .zshrc you just symlinked in.

One repo, two machines

The same script drives a fully-loaded laptop and a lean headless mini. It just checks the hostname:

case "$(scutil --get LocalHostName)" in
  openclaw*) IS_MINI=true ;;          # the headless CI mini
esac

BREWFILE="Brewfile"                    # laptop: full toolchain + GUI casks
$IS_MINI && BREWFILE="Brewfile.mini"   # mini: CLI only, no GUI
brew bundle --file="$BREWFILE"

The mini isn't a different setup — it's the same one with the GUI parts switched off. There's a third file, Brewfile.apps (App Store + GUI apps), run once by hand on a new laptop so routine syncs don't churn applications.

Chapter four

Secrets, in git, safely

The obvious objection to "commit everything" is secrets. You can't put API keys in a repo. Unless they're encrypted — which is exactly what sops + age do.

# secrets.env — committed to the (private) repo, values encrypted:
ANTHROPIC_API_KEY=ENC[AES256_GCM,data:+wTQ9u…,type:str]
OPENAI_API_KEY=ENC[AES256_GCM,data:wVJ3GN…,type:str]

# .zshrc, interactive shells only:
set -a; source <(sops -d ~/dotfiles/secrets.env); set +a

Key names stay readable; values are AES-256-GCM ciphertext. The whole file lives in git, so it's reproducible by git clone.

Why not 1Password? It needs an interactive unlock — it falls over in cron and CI. That's the same reason I'd already moved off the macOS Keychain for non-interactive use. sops + age is file-based and works everywhere a shell does.

The encrypted secrets are reproducible. The one age key that decrypts them is not in git — so it's the single thing you actually back up. Keychain, iCloud, and a printed copy. Lose it and the secrets are gone; that's the whole trade.

One macOS gotcha cost me an hour: sops looks for the key under ~/Library/Application Support/sops/age, not ~/.config. Set SOPS_AGE_KEY_FILE explicitly and it just works.

Chapter five

The fleet

Drift killed the mini once, so the goal isn't "auto-update everything" — it's visibility plus deliberate, policy-driven updates, all from the laptop:

mini-sync      # push my dotfiles to the mini (pull + bootstrap)
mini-status    # disk · CI runners online? · dotfiles vs origin: N behind

# topgrade, with a DIFFERENT policy per machine:
#   laptop.toml   → aggressive: latest everything
#   openclaw.toml → only = ["brew_formula","custom_commands"]   # conservative

A pre-push git hook nags me to run mini-sync whenever I push a shared dotfile, so the mini never silently falls behind. And the CI box never auto-updates the OS or chases casks — a surprise brew upgrade mid-build is a genuinely bad day. Conservative-on-the-CI-box is a choice, not an accident.

Chapter six

The scars

Everything that went wrong — and what each one taught me.

brew autoremove ate my keyboard's QMK toolchain. An untrusted Homebrew tap made its flashing tools look like orphaned dependencies, so autoremove swept them. Fix: declare them as explicit leaves; autoremove = false on the CI box.
qmk's vendored Python venv broke on the macOS beta. The Homebrew formula shipped a Python that didn't survive the OS bump. Fix: uv tool install qmk — a clean, isolated interpreter.
sops couldn't find its key. macOS looks in ~/Library/…, not ~/.config. Fix: set SOPS_AGE_KEY_FILE.
GitHub silently deletes idle self-hosted runners. The mini's runner had been deregistered for days and nobody noticed. Fix: surface runner status in mini-status.
"The mini has no Homebrew!" It did. A non-interactive SSH session just doesn't load it onto $PATH. A whole detour built on a false negative. Fix: eval "$(/opt/homebrew/bin/brew shellenv)" first.

uv all the way down

The through-line that kept surfacing: uv. uv tool install is a faster, cleaner pipx — even for non-Python CLIs (my keyboard firmware tool runs on it now). Pair it with mise for pinned, per-project Python and runtime versions, and "works on my machine" stops being a Python problem too.

uv tool install qmk        # the pipx successor, for any CLI
mise use python@3.14       # pinned, reproducible, no system-python roulette

Chapter seven

What to steal

I didn't just hope it would reproduce — I tested it. Clone the repo into a throwaway HOME and run bootstrap against it:

TESTHOME=$(mktemp -d)
git clone -q ~/dotfiles "$TESTHOME/dotfiles"
HOME="$TESTHOME" bash "$TESTHOME/dotfiles/bootstrap.sh"
#  → exit 0 · symlinks ✓ · oh-my-zsh ✓ · plugins ✓ · 0 errors

A reproducibility claim you haven't tested is a wish.

  • Declarative + idempotent beats a setup doc you'll never keep current.
  • sops + age lets secrets live in git, safely and non-interactively.
  • Reproducible ≠ Migration Assistant — you skip the accumulated cruft and keep only the intent.
  • Make drift visible. And the whole pattern transfers to any OS or team.

A new MacBook is now: install Command Line Tools, install Homebrew + gh auth login, clone, ./bootstrap.sh, drop in the age key. About twenty minutes to a working, themed, secret-loaded machine — that feels like mine.
