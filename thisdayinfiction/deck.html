CHAPTER · 01

The model.

Why datetime.date breaks on fiction.

THE PROBLEM

What works

from datetime import date

date(1955, 11, 5)   # Back to the Future ✓
date(2263, 3, 18)    # The Fifth Element ✓

What doesn't

date(year=None, month=4, day=4)  # 1984 — no year
# TypeError: integer argument expected, got 'NoneType'

Orwell never tells us what year it is. Python demands one.

This is the core design constraint. Python's date requires a year. Fiction doesn't always provide one. This drives the entire model design.
THE FIX

Three integers, not a date

class Event(models.Model):
    month = models.IntegerField()
    day   = models.IntegerField()
    year  = models.IntegerField(null=True, blank=True)

    source_year = models.IntegerField(null=True, blank=True)

year = when it happens in the story.
source_year = when the movie came out.

No DateField. No validation headaches. Just integers that can be NULL.

This is the key insight: don't use a date at all. Three nullable integers solve every edge case fiction throws at us.

Two kinds of "year"

year is the in-fiction date. When the story says it happens.

source_year is the real-world release. When the movie came out or the book was published.

They're almost never the same. And year might not exist at all.

CHAPTER · 02

Three APIs.

Matching titles to metadata across TMDB, Google Books, and Open Library.

THE CHAIN

The fallback chain

Every submission needs a cover image and metadata. Three APIs, tried in order.

  1. TMDB — movies & TV shows. Best metadata, great images. API key required.
  2. Google Books — literature. Good coverage, messy data. API key required.
  3. Open Library — literature fallback. Community-driven, no key needed. Free & open.

If TMDB returns a match, stop. Otherwise try Google Books, then Open Library. If all three miss, the event gets no cover image.

The chain matters because each API has different strengths. TMDB is great for visual media. Google Books has the widest literature coverage. Open Library is the safety net.
THE GOTCHA

Google Books: edition dates are not
publication dates

similar_years = [
    int(item['volumeInfo']['publishedDate'][:4])
    for item in items
    if fuzz.token_sort_ratio(query.lower(),
        item['volumeInfo'].get('title', '').lower()
    ) >= 70
]

first_pub_year = min(similar_years) if similar_years else None

Google Books has no year filter. Edition dates ≠ first publication.
Fix: fuzzy-match titles with rapidfuzz, collect all matching years, take the minimum.

This is a real gotcha. Search for "1984" and you get dozens of editions spanning 75 years. The 2023 reprint isn't the publication date. RapidFuzz solves the title matching; min() solves the date.
THE DISAMBIGUATION

The "Sag Harbor" problem

Searching for Colson Whitehead's novel Sag Harbor.
Google Books also returns travel guides, real estate listings,
and a local history of the actual town.

Before

query = "Sag Harbor"
# → 40 results, mostly about the real place

After

query = 'Sag Harbor inauthor:"Whitehead"'
# → 3 results, all the right book

When the title is also a real place, the author name is the only reliable disambiguator.

CHAPTER · 03

The crowd.

Letting strangers add data without chaos.

EQUIVALENCE

Same event, different strangers

Same month + day + normalized title = same event.
3 independent submissions = auto-approval. 

def normalise_title(title):
    title = title.lower().strip()
    title = re.sub(r'^(the|a|an)\s+', '', title)
    title = re.sub(r'[^a-z0-9\s]', '', title)
    return re.sub(r'\s+', ' ', title).strip()

"The Terminator", "the terminator", "Terminator" all collapse to terminator. Three people agree independently? It's probably real.

This is crowd-sourced verification without voting. If three strangers independently submit the same event, that's strong signal. The normalization handles cosmetic differences.
THE WINNER

Which submission wins?

Three people submitted the same event. We publish the most complete one.

def _completeness_score(event):
    return sum([
        bool(event.description),
        bool(event.cover_image_url),
        bool(event.creator),
        bool(event.source_year),
    ])

The submission with the most filled-in fields gets published. The rest are marked MERGED (not rejected). Everyone gets credit.

THE TRAP

The Rocky remake trap

Rocky (1976) and Rocky (2025) share a title.
Users submit events for both. The equivalence group sees 3 submissions
with the same normalized title... but conflicting source_year values.

Don't auto-approve. Send to admin.

Same title. Same date. Different movie.

The equivalence check isn't just title matching — it also validates that source_years are consistent within the group.

This is the edge case that makes naive crowd-sourcing dangerous. Remakes break the assumption that title + date = unique event. The source_year check catches it.
CHAPTER · 04

Earning trust.

Three tiers, automatic promotion, no gatekeeping.

PROMOTION

The trust ladder

  1. Registered — submissions go to the moderation queue.
  2. Trusted — bypasses the queue. Earned: 5 approved, <20% rejection.
  3. Admin — full control over events and users.
def qualifies_for_trusted(self):
    return (self.approved_count >= 5
            and self.rejection_rate() < 0.20)

No application process. No social proof. Just contribute good data and you're promoted automatically.

The philosophy: don't make people ask for trust. Let them earn it through contribution quality. The thresholds are intentionally low — we want to promote people.
PHILOSOPHY

MERGED, not REJECTED

When crowd consensus approves an event, the best submission is published.
The others are set to MERGED — not REJECTED.

All submitters get credit toward trust promotion.
Nobody is punished for contributing to consensus.

If three people saw the same thing, all three were right.
Only one gets published. All three get credit.
This is a values slide. The distinction between MERGED and REJECTED matters for user psychology. People who contribute valid data should never feel rejected, even if their version wasn't the one chosen.
CHAPTER · 05

What day is it?

Today depends on where you're standing.

THE FIX

Browser timezone → Django middleware

  1. JavaScript reads the browser timezone via Intl.DateTimeFormat.
  2. Stores it in a cookie: tdif_timezone.
  3. Django middleware reads the cookie, activates the timezone per request.
  4. timezone.localdate() returns the correct local date.

A user in Tokyo and a user in New York see different events at midnight. Both see the right ones.

This matters because the whole app is about "today." If we show the wrong today, nothing else works. The cookie approach is simple but has one nasty edge case...
THE BUG

The infinite loop

Cookies blocked → cookie write fails → reload to fix date → cookie still missing → reload again → forever.

INFINITE LOOP.

The fix: one line. 

sessionStorage.setItem('tz_tried', '1');

sessionStorage survives reloads but not tab closes. Check it before reloading. If the flag exists, don't reload — just serve UTC gracefully.

This is the laugh line. We shipped a reload loop to production. The fix is literally one line. SessionStorage is the unsung hero of browser state management.
